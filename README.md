# InsightHub — learn AI engineering by building a field medical insight engine

A hands-on, build-it-yourself tutorial that walks the six skills in Andrew Ng's AI
engineering skill map through **one continuous toy problem** in pharma Medical Affairs.

You will build **InsightHub**: a system that reads MSL call notes, congress abstracts
and publications for a (fictional) product, extracts discrete medical insights, clusters
them into themes, links them to evidence, answers analyst questions, and produces a
quarterly Field Medical Insight Report — with the compliance guardrails, evaluations and
production instrumentation that a real regulated deployment would need.

> ### Everything in `data/` is fictional
> Kestrel Bio, VELTRAXA® (zoltarimab), the AURORA trials, the competitors, the KOLs, the
> congress abstracts and every number in them were generated by `scripts/gen/`. None of
> it is medical information, none of it describes any real product, and none of it should
> ever leave this tutorial. Do not point any part of this repo at real HCP data, real
> call notes or real pharmacovigilance workflows.

---

## Why this problem

Ng's central claim is that AI engineering is *iterative*: you build, look at what came
out, and decide what to try next. A tutorial that hands you a finished system teaches you
nothing about that loop. So this one is built around the loop.

The MSL insight problem is a good vehicle because it is genuinely hard in the ways AI
systems are hard:

| What makes it hard | Which skill it forces you to learn |
|---|---|
| "Insight" has no crisp definition — two smart people label the same note differently | Evaluation-driven development |
| The same underlying insight appears in 20 notes in 20 different wordings | Grounding, embeddings, clustering |
| The model has never heard of your drug | Grounding models with data |
| A missed adverse event mention is a regulatory event, not a bug | Guardrails, risk-calibrated testing |
| 8 MSLs × 15 notes/week × 50 weeks is a real cost line | Model routing, caching, batching |
| Questions like "what changed since ECCO?" need a plan, not a prompt | Agentic systems |
| Which insights reach the strategy team is a ranking problem with labels | Machine learning foundations |

## The eight chapters

| # | Chapter | Skill | You will build |
|---|---|---|---|
| 0 | [Orientation](tutorial/00-orientation.md) | — | Setup, the dataset, and the loop you'll run 30 times |
| 1 | [LLM foundations](tutorial/01-llm-foundations.md) | LLM foundations | Your first extractor; tokens, context budget, sampling, structured output, caching, model choice |
| 2 | [ML foundations](tutorial/02-ml-foundations.md) | ML foundations | A calibrated insight-triage classifier, and the baseline that beats your LLM |
| 3 | [Grounding with data](tutorial/03-grounding-with-data.md) | Grounding | Document pipeline, hand-built vector index, hybrid search, semantic layer, KOL graph, retrieval evals |
| 4 | [Agentic systems](tutorial/04-agentic-systems.md) | Agents | Ingestion workflow → analyst agent loop → tools, memory, guardrails, prompt injection, multi-agent report |
| 5 | [Eval-driven development](tutorial/05-eval-driven-development.md) | Evals | Error analysis, failure taxonomy, code evals, an LLM judge you actually validate, three measured iterations |
| 6 | [Operating in production](tutorial/06-operating-in-production.md) | Production | Tracing, online metrics, drift, regression CI, incident response, cost/latency optimisation |
| 7 | [Capstone](tutorial/07-capstone.md) | All | Open-ended extensions and a self-assessment rubric |

Chapters build on each other. Do them in order the first time.

**Time:** roughly 20–30 hours end to end. Chapter 5 is the longest and the most
important; do not skip it to get to Chapter 6.

**API spend:** the whole tutorial runs comfortably under $15 if you follow the model
routing advice. Chapter 1 shows you how to measure it as you go.

## Setup

```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # then paste your API key
export PYTHONPATH=$PWD/src
python -c "from insighthub.config import check; check()"
```

Expected: `OK. 140 call notes, models: ...`

Get an API key at <https://console.anthropic.com>. There is no package install step —
`export PYTHONPATH=$PWD/src` (or adding `src/` to your IDE's path) is all `import
insighthub` needs; `conftest.py` handles it for pytest.

Regenerate the dataset at any time (it is deterministic — same bytes every run):

```bash
make data           # or: python scripts/gen/generate.py && python scripts/gen/make_binaries.py
```

### Running without spending anything

Two escape hatches let you exercise most of the machinery offline:

```bash
export INSIGHTHUB_EMBED_BACKEND=hash    # a non-semantic embedder; no model download
make test                                # 20 deterministic tests, no API key
python scripts/make_mock_run.py --out runs/fixture.jsonl        # a synthetic extraction run
python -m insighthub.evals.run --run runs/fixture.jsonl --split dev
```

The `hash` backend deliberately makes retrieval bad, so you notice if you leave it on. It
exists so CI (and you, on a plane) can run the deterministic layers. Unset it before
believing any retrieval number.

### A note on the numbers in the chapters

Blocks marked **Measured** come from running the code in this repo and you should
reproduce them closely. Blocks marked *Illustrative* show the **shape** of a result —
what the numbers mean in relation to each other — using plausible values, because they
depend on a live model. Never copy a number you did not produce into your decision log.

## What's in `data/`

```
data/
  call_notes/         140 MSL call notes (.txt) + manifest.csv
  kols/               40 KOL records (kols.csv)
  congress/           30 fictional congress abstracts (.md) + index.csv
  publications/       12 fictional publications (.md) + index.csv
  product/            VELTRAXA medical affairs fact base
  taxonomy/           the 12-category insight taxonomy + flags + strategic priorities
  eval/
    gold_insights.jsonl      ground truth for all 140 notes (dev/test/holdout splits)
    retrieval_queries.jsonl  30 queries with relevant note ids
    judge_calibration.jsonl  60 human-labelled judge examples
  ml/                 2,000-row historical insight-review table (16% positive)
  raw/                deliberately messy inputs: HTML, OCR'd text, dirty CSV, PDF, poster PNG
```

The gold labels exist because the data is synthetic. **Do not look at
`gold_insights.jsonl` before Chapter 5 asks you to.** Chapter 5's whole point is that in
real life you build the labels yourself by looking at outputs, and the exercise only
works if you do that first.

## What's in `src/insighthub/`

Chapter-by-chapter, so you can see where each piece comes from:

| Module | Chapter | What it is |
|---|---|---|
| `config.py`, `corpus.py` | — | Paths, model routing, loaders. Provided; no TODOs. |
| `llm.py` | 1 | Instrumented Messages API wrapper. Every call goes through here. |
| `extract.py` | 1 | Insight extraction with a tool-schema output contract. |
| `triage.py` | 2 | Calibrated ranking model for the review queue. |
| `docs.py` | 3 | HTML/PDF/OCR/CSV → LLM-ready text; section-aware chunking. |
| `embed.py`, `index.py` | 3 | Embeddings + a vector and BM25 index written from scratch. |
| `semantic.py` | 3 | A semantic layer over KOL data (instead of text-to-SQL). |
| `themes.py` | 3 | Cluster with maths, name with an LLM. Plus a small KOL/theme graph. |
| `retrieval_eval.py` | 3 | recall@k, MRR, nDCG, bootstrap CIs. |
| `pipeline.py` | 4 | The deterministic ingestion DAG. |
| `tools.py`, `agent.py` | 4 | Tool registry and a hand-written agent loop. |
| `guardrails.py` | 4 | Compliance gates, injection defences, output guards. |
| `report.py` | 4 | Multi-agent fan-out/fan-in for the quarterly report. |
| `evals/` | 5 | Code evals, matching, a validated LLM judge, the suite runner. |
| `observability.py` | 6 | Tracing, metrics, drift, alerting. |
| `serve.py` | 6 | FastAPI service with trace IDs, versions and a feedback endpoint. |

Plus `scripts/` (one per experiment the chapters ask you to run), `tests/` (deterministic
only), and `.github/workflows/evals.yml` (two-tier CI).

## The one habit this tutorial is trying to install

Every chapter ends with a **Decision Log** entry:

> *What we observed → what we hypothesised → what we changed → what happened → what we
> chose to do next, and what we chose NOT to do.*

Keep your own in `DECISIONS.md` (there's a template with an example entry). The log, not
the code, is the artefact that makes you an AI engineer rather than someone who has used
an API.

## If you only have two hours

Do Chapter 0 §0.5 (label ten notes by hand, write your definition), then Chapter 5 §5.2
(open coding on the mock run) and §5.6–5.7 (validate a judge). Those three sections
contain the skill; everything else is the material it operates on.
